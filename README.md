# ai-assisted-learning-portal

A sandbox project for experimenting with **LLMs** and **Streamlit** by building **context-aware math problems**.

The idea is to prompt a language model with user context — grade level, topic, subtopics (e.g. multiplication, subtraction), thematic setting, and difficulty — and receive a structured math problem back. [Pydantic](https://docs.pydantic.dev/) enforces the shape of that output, and [pydantic-ai](https://ai.pydantic.dev/) wires the model call so responses map cleanly onto typed Python objects. A Streamlit front-end (planned) will let you tweak context in the browser and see generated problems interactively.

## Run

**Prerequisites:** Python 3.14+, [uv](https://docs.astral.sh/uv/), and a Google Gemini API key.

```bash
# Clone and enter the project
cd pydantic-sandbox

# Install dependencies
uv sync

# Add your API key (used by pydantic-ai / Gemini)
echo 'GOOGLE_API_KEY=your-key-here' > .env

# Generate a context-aware math problem via LLM
uv run run-app
```

**Streamlit UI (planned):** once a Streamlit app is added, start it with:

```bash
uv run streamlit run app.py
```

## LLM-as-a-Judge Verification (multi-judge)

Math problems are generated by `gemini-3.5-flash` and — when judges are passed in — verified by a **judge ensemble** (multi-judge evaluation): independent verifiers must all agree before a task is accepted.

- **Wolfram|Alpha** is the ground-truth judge. It can't parse themed narrative, so the problem's `text` is first translated into a bare arithmetic expression using the judge's own Groq-hosted Llama model (independent of the generator). The expression is computed by Wolfram and compared with the `correct_answer` the LLM produced.
- **Qwen** (`qwen/qwen3.6-27b`, via Groq) is an independent LLM judge, specialized for math. It is fed the problem `text` directly and produces a single answer, which is compared with `correct_answer`. Different model family, different provider — it does not share the generator's or the Wolfram translator's blind spots.

**Setup:**

1. Get a Wolfram|Alpha App ID from <https://developer.wolframalpha.com/>
2. Get a Groq API key from <https://console.groq.com/> — it powers the Wolfram judge's translation pass (`groq:llama-3.3-70b-versatile`) and the Qwen judge (`qwen/qwen3.6-27b`), both independent of the Gemini generator. Without a Groq key the Wolfram judge falls back to the Gemini model (less independent) and the Qwen judge is disabled.
3. Add the keys to `.env`:

```bash
echo 'WOLFRAM_APP_ID=your-app-id' >> .env
echo 'GROQ_API_KEY=your-groq-key' >> .env
```

Any key you omit disables that judge; with no keys at all the demo skips verification.

**Flow:**

1. `MathProblemGenerator.generate()` runs a single loop: generate → validate → (optionally) judge.
2. Each attempt calls the LLM and validates the response against the `GeneratedTask` schema.
3. When judges are provided (a single judge or a list), the task is verified by every judge. Wolfram translates `text` into a bare arithmetic expression (retried only on transient translation errors — no faithfulness pass), computes it via the Short Answers API (`v1/result`), and compares with `correct_answer`. Qwen is fed the `text` directly; its `<think>`-wrapped reasoning is stripped and the final answer is compared with `correct_answer` (a rate limit or transport failure is treated as unverifiable, like Wolfram's 501).
4. The task is accepted only when **all** judges verify it. A failure from any judge is fed back to the LLM as corrective feedback — without leaking any judge's answer — and retried, up to `retries` attempts (default 5).
5. Returns the validated `GeneratedTask`, or raises `RuntimeError` after `retries` failed attempts.

**Usage:**

```python
from agentic_learning_portal.domains.math import (
    MathProblemGenerator,
    MathProblemGenerationPromptInput,
    QwenMathJudge,
    WolframAlphaJudge,
)

judges = [WolframAlphaJudge(), QwenMathJudge()]

task = await MathProblemGenerator().generate(
    prompt_input=input,
    judge=judges,
    retries=5,
)
```

**Note:** Wolfram|Alpha is a computational knowledge engine, not an LLM. It serves as ground truth — it computes the answer from the translated expression independently of the language model that wrote the task. The judge's translation pass uses its own `model`, defaulting to `groq:llama-3.3-70b-versatile` — a different model family (via Groq) than the Gemini generator, so the judge does not share the authoring LLM's blind spots. Override with `WolframAlphaJudge(model="...")`. Qwen adds an independent LLM opinion: `qwen/qwen3.6-27b` (a reasoning model on Groq — a different model family than the Gemini generator and the Llama translator) is fed the problem text and outputs a single answer; override with `QwenMathJudge(model="...")`. When both judges agree with `correct_answer`, their answers are mutually consistent — the consensus check is what makes the panel more reliable than any single verifier.

## Architecture

The project is split into a generic **API layer** and domain-specific implementations that plug into it.

### API layer (`api/`)

- `model.py` — `ProblemGenerationPromptInput` (abstract base; subclasses implement `build_user_prompt()`), `GeneratedTask` (base output schema), `VerificationResult` (a judge's verdict), and `Judge` (the interface both verifiers implement).
- `generator.py` — `Generator` calls a `pydantic_ai` `Agent` and validates the response against the expected output class. If validation fails, the response and error are folded into a corrective retry prompt and re-sent (up to `n_retry`, default 5) before raising.

### Domain layer (`domains/math/`)

- `model.py` — `MathProblemGenerationPromptInput` adds domain fields (`topic`, `subtopics`, `context`, `complexity`, `grade`) and builds the user prompt.
- `generator.py` — `MathProblemGenerator` pins the output type to the api layer's `GeneratedTask` and supports a single judge or a list of judges (all must verify — judge ensemble).
- `wa_judge.py` — `WolframAlphaJudge(Judge)`: translates `text` into a bare arithmetic expression, computes it with Wolfram|Alpha's Short Answers API, compares with `correct_answer`.
- `qwen_judge.py` — `QwenMathJudge`: feeds `text` to `qwen/qwen3.6-27b` via Groq's OpenAI-compatible chat API, extracts a single answer (stripping `<think>` reasoning), compares with `correct_answer`.
- `_comparison.py` — answer-comparison helpers shared by both judges (`_answers_match`, `_to_number`, `_normalize`).
- `__init__.py` — re-exports the domain's public API.

### Generation flow

`MathProblemGenerator.generate(prompt_input)` → `prompt_input.build_user_prompt()` → the base class's `call_llm_with_output_feedback_loop` (LLM call + schema validation) returns a validated `GeneratedTask`; the math generator adds judge verification on top. Both judges implement the api layer's `Judge` interface. The default model is `google:gemini-3.5-flash`, overridable via `Generator(model=...)`; the Wolfram judge's translation defaults to `groq:llama-3.3-70b-versatile`, overridable via `WolframAlphaJudge(model=...)`; the Qwen judge defaults to `qwen/qwen3.6-27b`, overridable via `QwenMathJudge(model=...)`. When a list of judges is passed, the task is accepted only when every judge verifies it.

### Adding a new domain

Follow the math pattern: subclass `ProblemGenerationPromptInput` (implement `build_user_prompt()`), define an output model, and subclass `Generator` to pin the output type.

## Tech stack

- **Python 3.14** — managed with **uv**
- **Pydantic v2** — structured data and validation
- **pydantic-ai** — LLM integration with typed outputs
- **Google Gemini** — default model (`google:gemini-3.5-flash`)
- **Groq / Llama 3.3 70B** — Wolfram judge's translation model (independent of the generator)
- **Groq / Qwen3.6-27B** — independent LLM math judge
- **Wolfram|Alpha** — ground-truth judge (Short Answers API)
- **Streamlit** — planned UI for context inputs and live problem generation
